NOTE: I run audiod on Slackware64-current, so a PipeWire session is
always up. Upstream issue #41 (hangs on the loading screen unless
another session is running) does not reproduce here for that reason:
the shell blocks on a PulseAudio client that never connects otherwise.

Fixed so far:
=============
- The compositor no longer dies when it receives an unmapped key.
  send_key_event() returns Err for any keycode missing from
  XKB_TO_PHYSICAL_KEY_MAP and both call sites used .expect(), so one
  unknown key took down the session and every client with it. Connecting
  a Bluetooth audio device was enough: BlueZ creates an AVRCP input
  device that emits KEY_PLAYCD, which the map did not contain.

- wl_callback.done() carries a monotonic timestamp instead of always
  reporting zero. start_time was created on the line above the loop that
  sent the callbacks, so elapsed() was never more than a few
  microseconds. Clients derive their animation delta from that value and
  concluded no time had passed, which is what left Firefox content areas
  and video players blank.

- The path libapp.so is loaded from is no longer hardcoded to
  /usr/lib/veshell, which does not exist on distributions that separate
  32- and 64-bit libraries. On Slackware64 the compositor started,
  failed to find the AOT snapshot and exited immediately. It now comes
  from VESHELL_LIB_DIR, the variable the build script already uses for
  the RPATH; VESHELL_DATA_DIR does the same for the asset bundle.

- The full xkb configuration is settable, not just the layout. rules,
  model, variant and options never reached XkbConfig, and without
  options there is no way to set a group toggle -- a second layout could
  be loaded but never reached. Greek works now. Existing settings.json
  files are unaffected; the new keys all default to empty.

- veshell-session falls back to dbus-run-session where there is no user
  service manager, instead of printing "No systemd or dinit detected"
  and giving up. That made the .desktop entry a display manager reads
  useless on Slackware, Void, Alpine, Gentoo and the BSDs. It also keeps
  a log of each session under /tmp, because a compositor that dies takes
  its terminal with it and the panic message goes with it.

- Six unwraps that a client could reach have been made fallible. These
  all ran inside wl_display dispatch callbacks -- extern "C" frames that
  cannot unwind -- so a panic there did not unwind into an error, it
  called abort() and took the compositor and every client down with it:

    * construct_subsurface_role_message() unwrapped get_parent(). A
      surface can still carry SUBSURFACE_ROLE after its wl_subsurface is
      destroyed, or while the parent is being torn down. Opening a tab
      in Firefox was enough to hit this.
    * the recursive subsurface commit unwrapped a lookup into the
      surface map, which can miss a child that is not registered yet or
      is already gone.
    * a popup's meta popup was unwrapped before its initial configure,
      although the popup can be committed before the shell knows of it.
    * move_request and resize_request unwrapped the meta window, so a
      client asking to be moved before the shell had created one killed
      the session.
    * constrain_popup_to_parent unwrapped the root toplevel, which is
      not an xdg toplevel at all when the chain roots in XWayland.

  The popup parent chain in new_popup was the worst of them: three
  unwraps and a while loop with no exit. A chain whose parent id was in
  neither map panicked, and one pointing back at itself spun forever
  with the compositor wedged. It now walks with a bound and bails out
  cleanly. Upstream had left a "TODO: Revise this unwrap" on it.

Still broken:
=============
- Window layout is not persisted
- Text input breaks on certain transform matrices
- wp_viewporter is missing
- No screencopy protocol, so screenshots are impossible
- flutter_svg throws on icons with pattern elements lacking a viewBox,
  which empties the application drawer
- Two zwp_linux_dmabuf_v1 globals are created in drm_backend.rs
- get_settings() re-reads and re-parses both settings files on every
  key press
- Around 340 unwrap/expect calls remain. Most are in initialisation,
  where aborting is the right answer, but the dispatch paths deserve
  another pass.
